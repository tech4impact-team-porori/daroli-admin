# 대시보드 재설계 — 액션 중심으로

> 2026-08-18 · 정승환
> **⚠️ 이 문서는 앱 기획서 Ver 1.0 B-1(운영 대시보드)의 변경 제안입니다.**
> 원문은 🟦 확정 사항이므로 **팀 승인 후** 적용합니다. 승인 전까지는 현재 3탭 구조를 유지합니다.

---

## 1. 왜 바꾸나

### 제기된 의견

- 기능이 많아서 복잡해 보인다
- 소규모 활동이므로 기능이 겹치지 않게 구성
- 대시보드는 긴급 위주로, 나머지는 각 카테고리로
- 메인은 **당장 처리해야 하는 업무** 중심, 현황은 간단한 통계로

### 코드를 열어보니 실제로 겹칩니다

| 대시보드에 있는 것 | 이미 있는 곳 | 판정 |
|---|---|---|
| 탭2 매니저별 지급 현황 표<br>(매니저명 / 이달 활동 / 승인 정산액 / 지급 완료 / 잔액) | `/managers` 표 12컬럼에 **5개 전부 포함** | 🔴 완전 중복 |
| 탭1 예산 현황 4단계 · 이번 달 예산 현황 | `/payments` 요약 카드 3종 + 월별 정산표 | 🟠 부분 중복 |
| 탭2 지역별 매니저 현황 표 | 탭3 지역별 돌봄 수요 표 | 🔴 같은 지역 축 표가 2개 |
| 통합 지역 지도 | 탭2·탭3에 각각 1개씩 | 🔴 같은 컴포넌트 2회 |

**규모를 생각하면 과합니다.** 매니저 7명, 대상자 22명입니다. 매니저 7행짜리 표를 두 화면에 두는 건 유지보수 비용만 늘립니다.

### 더 근본적인 문제

지금 대시보드는 **"현황판"** 입니다. 숫자를 보여주지만 *무엇을 해야 하는지*는 말해주지 않습니다. 관리자가 아침에 이 화면을 열었을 때 알아야 하는 건 "예산 사용률 6.2%"가 아니라 **"승인해놓고 아직 안 준 돈이 124만원 있다"** 입니다.

## 3. 새 구조

```
대시보드 (/)
│
├─ ① 지금 처리할 일          ← 화면의 60%. 이게 주인공
│    처리할 게 있는 항목만 표시. 0건이면 그 줄 자체가 안 보임
│
├─ ② 이번 달 현황            ← 통계 타일 4개, 한 줄
│
└─ ③ 활동 추이 (6개월)       ← 작게. 제출/승인 2계열
```

**탭을 없앱니다.** 탭이 3개라는 건 화면 하나에 서로 다른 관심사가 3개 들어있다는 뜻이고, 그게 "복잡해 보인다"의 원인입니다.

## 4. ① 지금 처리할 일 — 액션 큐 명세

### 정렬 원칙

> **사람이 기다리는 것 > 일이 밀리는 것 > 준비가 안 된 것**

돈을 못 받은 매니저와 방문을 기다리는 어르신이 최우선입니다. 통계는 나중에 봐도 되지만 이건 오늘 처리해야 합니다.

### 항목 8종

| # | 항목 | 조건 | 표시 | 이동 |
|---|---|---|---|---|
| 1 | 🔴 **정산 필요** | `budget.approvedUnpaid > 0` | 금액 + "승인됐지만 아직 매니저에게 안 나갔습니다" | `/payments` |
| 2 | 🔴 **출금 신청 대기** | `PAYOUT_STATUS.REQUESTED` 건수 > 0 | 건수 + "매니저가 지급을 기다리는 중" | `/payments` |
| 3 | 🟠 **일지 검토 대기** | `LOG_STATUS.PENDING` 건수 > 0 | 건수 + "가장 오래된 건 N일 경과" | `/review` |
| 4 | 🟠 **배정 지연 요청** | `REQUEST_STATUS.REQUESTED` 이면서 접수 후 24시간 경과 | 건수 + "24시간 넘게 매니저 미배정" | `/requests` |
| 5 | ⚪ **매니저 심사 대기** | `applied` + `educated` 인원 > 0 | 인원 + 다음 단계 안내 | `/managers` |
| 6 | ⚪ **미배정 대상자** | `managerId` 없는 대상자 > 0 | 인원 + "배정해야 지역별 통계에 잡힘" | `/recipients` |
| 7 | ⚪ **매니저 부족 지역** | `isShortage` 인 지역 > 0 | 지역 수 + 지역명 나열 | `/managers` |
| 8 | ⚪ **배정 예산 미설정** | `needsMonthlyBudgetSetup()` | "이번 달 배정 예산이 설정되지 않았습니다" | `/settings` |

색: 1·2 = danger / 3·4 = warning / 5~8 = 중립(회색)

### 표시 규칙

- **0건인 항목은 줄 자체를 렌더링하지 않습니다.** "0건" 을 보여주는 건 소음입니다
- 항목 전체가 0이면 → `지금 처리할 일이 없습니다` 한 줄 + 통계만 표시
- 3번의 "N일 경과"는 가장 오래된 `pending` 일지 기준. 이게 있어야 급한 정도가 보입니다
- 클릭하면 해당 화면으로 이동하되, **필터가 걸린 상태로** 이동합니다
  (예: 일지 검토 → 상태=검토 대기로 필터된 상태)

### 🔴 4번 "배정 지연"에 대해

`/requests` 화면에 이미 `STALE_HOURS = 24` 기준의 "배정 지연" 배지가 있습니다(Phase 9에서 🟨 제안으로 채택). **같은 상수를 씁니다.** 두 곳에서 기준이 갈리면 숫자가 안 맞습니다.

## 5. ② 이번 달 현황 — 통계 4종

| 타일 | 값 | 보조 |
|---|---|---|
| 활동 건수 | 이번 달 승인 일지 수 | "승인 기준" |
| 활동 중인 매니저 | `active` 인원 | "전체 N명 중" |
| 관리 대상자 | 전체 인원 | "어르신 N · 아동 M" |
| 예산 사용률 | `usageRate` | 남은 금액 |

**전부 "보기만 하는" 숫자입니다.** 여기에 액션을 붙이지 않습니다. 액션은 ①에만 있습니다 — 그래야 "어디를 봐야 하지?"가 안 생깁니다.

모든 숫자에 기준을 붙입니다. "55건"이 아니라 "55건 · 승인 기준".

## 7. 데이터 요구사항

`DashboardData` 타입에 액션 큐용 필드가 추가돼야 합니다. **전부 기존 데이터에서 계산 가능**하므로 백엔드 스키마 변경은 없습니다.

```ts
export interface ActionQueue {
  approvedUnpaid: Won            // 1  (BudgetSummary에 이미 있음)
  requestedPayoutCount: number   // 2
  pendingLogCount: number        // 3  (DashboardData에 이미 있음)
  oldestPendingDays: number      // 3  신규
  staleRequestCount: number      // 4  신규 (24시간 기준)
  pendingManagerCount: number    // 5  신규 (applied + educated)
  unassignedRecipientCount: number // 6 신규
  shortageRegions: Region[]      // 7  regions에서 isShortage 필터
  needsBudgetSetup: boolean      // 8  calc.needsMonthlyBudgetSetup()
}
```

판정 로직은 **전부 `lib/calc.ts` 에** 둡니다. 화면에서 계산하지 않습니다 (CLAUDE.md 절대 규칙 2).

`lib/data/index.ts` 의 `getDashboard()` 반환 타입에 `actions: ActionQueue` 추가.

기획서 Ver 1.0 대비 실제로 달라지는 것만 추리면 이렇습니다.

| 변경 | 내용 | 위험 |

| **매니저별 지급 현황 표 제거** | `/managers` 와 완전 중복 | 낮음 |
