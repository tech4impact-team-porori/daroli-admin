| 표기 | 뜻 |
|---|---|
| 🟦 **확정** | 기획서 Ver 1.0 원문에 있는 내용. **임의로 바꾸지 않는다** |

## 0. 시작 전에

**① DB가 미정이라는 게 오히려 유리하다.**
DB를 기다리면 아무것도 못 만든다. 대신 **데이터를 가져오는 통로를 함수 한 겹으로 격리**하고 그 안을 가짜 데이터로 채운다. 나중에 개발자 DB가 나오면 그 함수 내부만 갈아끼운다. 화면 코드는 한 줄도 안 바뀐다. → 4-1.

**② 이 대시보드가 대체하는 것은 "HWP 활동일지 + 엑셀"이다.**
현재 운영 담당자는 매니저가 HWP로 쓴 일지를 받아 엑셀로 집계해 활동비를 정산한다. 성패는 화면이 예쁜지가 아니라 **그 반복 작업이 실제로 사라지는지**로 결정된다.

**③ 🟦 관리자 사이트 분리는 이미 채택됐다.**
원문 4장 논의사항에서 **"관리자 사이트 별도 개설 → 채택"**. 3개 역할이 한 앱에 로그인하는 구조가 불편하다는 이유. 즉 **내가 만드는 건 독립된 관리자 웹**이다. 매니저·요청자 화면은 내 범위가 아니다.

## 1. 대시보드 구성

### 1-1. 🟦 화면 목록 (원문 IA 그대로)

원문에는 화면마다 **화면 ID**가 붙어 있다. 개발자와 이야기할 때 이 ID로 부르면 서로 헷갈리지 않는다.

| 경로 | 화면 | 화면 ID |
|---|---|---|
| `/` | 운영 대시보드 — 탭 1 예산 | `admin-dashboard-budget` |
| `/` | 운영 대시보드 — 탭 2 매니저 | `admin-dashboard-managers` |
| `/` | 운영 대시보드 — 탭 3 돌봄 수요자 | `admin-dashboard-recipients` |
| `/requests` | 돌봄 요청 현황 | `admin-requests` |
| `/review` | 활동일지 검토 | `admin-review` |
| `/recipients` | 대상자 관리 | `admin-recipients` |
| `/managers` | 매니저 관리 | `admin-managers` |
| `/payments` | 활동비 관리 | `admin-payments` |

**공개 영역** (`public-login`, `public-apply`)은 매니저 지원 접수 → `/managers` 로 들어오는 입구다. 관리자 웹을 분리한다면 **`/apply` 는 매니저 앱 쪽에 남고, 나는 그 결과만 `/managers` 에서 받는다.** → 🔴 확인 필요 (부록 C-4)

## 2. 화면별 상세 명세

### 2-0. 공통 규약

**🟦 상태 값 (원문 표기)**

원문에 영문 값이 명시된 것만 확정으로 표시한다. **이 영문 문자열이 실제 DB에 저장되는 값**이고, 나와 개발자가 철자까지 똑같이 써야 숫자가 맞는다.

```
매니저 자격    applied → educated → active        🟦 원문 명시
              + 비활성(inactive)                  🔴 영문값 원문 미표기

요청 상태      requested → proposed → confirmed → completed / cancelled   🟦 원문 명시

일지 상태      검토 대기 → 승인 / 반려             🔴 영문값 원문 미표기
              원문에 'pending'만 등장 (B-6 재산정 규칙)

출금 상태      대기 → 지급 완료 / 반려             🔴 영문값 원문 미표기

정산 상태      산정 → 승인 / 승인 취소             🔴 영문값 원문 미표기
```

> **내가 아까 "enum은 기획서에 없다"고 한 건 틀렸습니다.** 요청 상태와 매니저 자격은 원문에 영문으로 박혀 있습니다. 다만 **일지·출금·정산 상태는 한글 개념만 있고 영문 값이 없어서**, 이건 개발자와 정해야 합니다. (부록 C-1)

**🟦 매니저 상태 필터 명칭** (B-5 원문)
`활동 가능` / `승인 대기` / `신청 완료` / `비활성` — 화면에 이 한글로 표시한다.
🔴 `승인 대기`=educated, `신청 완료`=applied 로 보이지만 원문에 대응이 명시되지 않았다. 확인 필요.

**🟨 상태 색 규약** (원문에 없음 — 내가 정함)

| 의미 | 색 |
|---|---|
| 대기·검토중 | amber |
| 진행·확정 | blue |
| 완료·승인 | emerald |
| 반려·취소 | rose |
| 부족 경고 | red 테두리 |

**🟦 레이아웃** — 좌측 사이드바 7메뉴(대시보드/요청 현황/일지 검토/대상자 관리/매니저 관리/활동비 관리/설정) + 우측 콘텐츠. 원문 화면 캡처와 동일.

### 2-1. `admin-review` — 활동일지 검토 ★ 가장 먼저 만들 화면

**🟦 필터**: 월 / 상태(검토 대기·승인·반려) / 매니저

**🟦 일지 카드** — 원문은 **카드 형식**이다. 카드 안에 들어가는 항목:

```
대상자 / 매니저
활동 일시 · 활동 유형
활동 장소
참여 인원          ← 내가 이전 버전에서 빠뜨렸던 항목
활동 내용
특이사항
첨부 사진
GPS 위치 · 거리 정보
```

**🟦 액션**: [승인] / [반려] → 반려 시 **사유 입력 다이얼로그, 사유 필수**

**🟦 규칙**: **승인된 일지만 월별 정산 산정에 포함**

> 🟨 이전 버전에서 제가 "좌 목록 / 우 상세 2단 레이아웃"이라고 썼는데, **원문은 카드 목록**입니다. 원문을 따릅니다. 카드가 길어져서 검토가 느려지면 그때 2단을 제안하겠습니다.

🟨 **추가 제안**
- GPS 없는 수동 완료 건에 배지 — 감사 때 이 건들만 따로 뽑을 수 있어야 함
- 다건 일괄 승인은 **만들지 않는다** — 검토가 형식화되면 사업 요건 위반
- 정렬 기본값을 오래된 순으로 (대기가 쌓이지 않게)

### 2-2. `admin-payments` — 활동비 관리 ★ 돈 나가는 화면

**🟦 구성**
- 월 선택 · **[월별 정산 생성(재산정)]** 버튼
- 요약 카드 3종: **해당 월 산정 총액 / 대상 매니저 수 / 출금 신청 대기 건수**
- 출금 신청 처리 표: 매니저 · 신청 금액 · [지급 완료] / [반려(사유 입력)]
- 월별 정산 표: 매니저별 **활동 건수 × 단가 = 산정액** · [승인] / [승인 취소]

**🟦 규칙**
1. **정산 승인 → 그 금액이 매니저의 출금 가능 잔액에 적립**
2. **재산정은 미승인(pending) 건만 갱신**
3. **승인 취소는 잔액이 음수가 되지 않을 때만 허용**
4. **잔액 = 승인 정산 총액 − (신청 중 + 지급 완료 출금)** ← 매니저 화면 C-5 규칙이지만 계산식은 공용
5. **잔액 초과 신청은 서버에서 차단**
6. **반려된 출금 금액은 잔액으로 복귀**

> **여기서 중요한 구조 하나:** 정산은 **자동이 아니다.** [정산 생성] → [정산 승인] → 그제서야 잔액 적립. 즉 **승인이 두 번**이다 — 일지 승인(`/review`)과 정산 승인(`/payments`). 이전 버전에서 제가 이걸 하나로 뭉갰습니다.

🟨 **추가 제안 — 서버 가드 2종**
7. 지급 완료 건은 수정 불가
8. 출금 처리 멱등성 — 같은 신청을 두 번 처리해도 한 번만 나가게 (**멱등성**: 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질. 버튼 두 번 눌러서 돈이 두 번 나가는 걸 막는다)

→ 5~8은 **개발자에게 서버에서 막아 달라고 요청할 항목**(4-3). 프론트에서만 막으면 감사에서 문제가 된다.

### 2-3. `admin-settings` — 시스템 설정

**🟦 요소**: 활동 1회 기준 단가(원) / 사업 전체 예산(원) / 이번 달 배정 예산(원) / [설정 저장]
**🟦 규칙**: 단가는 0보다 커야 함. **예산 0 = 미설정**

🟨 **추가 제안**
- 단가 변경 시 영향 범위(미승인 건 산정액 전부 변경)를 확인 다이얼로그로 안내
- 변경 이력 저장
- "매니저 1명당 대상자 N명" 판정 기준을 여기로 (원문은 3 고정)

> 화면은 가장 단순하지만 **모든 금액이 이 값을 참조**한다. 그래서 정산 다음으로 만든다.

### 2-4. `admin-managers` — 매니저 관리

**🟦 엑셀형 목록 표** — 컬럼 전부:
```
이름·연락처 / 상태(배지) / 거주 지역 / 활동 지역(태그) / 자차 /
담당 대상자 수 / 이번 달 활동 / 누적 활동 /
승인 누적액 / 지급 완료액 / 잔액 / 관리
```
**🟦 하단 합계 행** (활동 건수·금액 합산) ← 이전 버전에서 빠뜨림
**🟦 필터 바**: 이름·이메일·지역 검색 / 상태 필터 4종
**🟦 심사 액션**: [교육 이수 확인] → [활동 승인] (applied → educated → active)
**🟦 활성/비활성 전환**

**🟦 규칙**
- **active 이후에만 요청 배정·활동일지 작성 가능**
- 금액 통계는 **출금 가능 잔액과 동일한 산식** 사용 (= 승인 누적액 − 지급/신청액)

> 매니저 6명(화양읍1·청도읍3·매전면1·금천면1·풍각면1)이지만 **확장 계획이 있다.** 6명 기준으로 하드코딩하지 말 것.

### 2-5. `admin-recipients` — 대상자 관리 🔴 개인정보 최고 위험 화면

**🟦 엑셀형 목록 표**:
```
이름 / 유형(어르신·아동 배지) / 지역(태그) /
담당 매니저(태그, 미배정 시 경고 배지) /
돌봄 필요사항 / 상세 주소 / 관리(수정·삭제)
```
**🟦 필터 바**: 이름·지역·매니저 검색 / 유형 필터 / 담당 매니저 필터(**미배정만 보기** 포함)
**🟦 액션**: [신규 등록] / 등록·수정 다이얼로그(**이름 필수**, 지역은 읍·면 선택) / 삭제 확인 다이얼로그
**🟦 규칙**: **대상자마다 담당 매니저 배정 가능 — 이 배정 정보가 지역별 통계의 기준**

## 3. 디자인 레퍼런스

### 3-1. 톤

원문 화면 캡처를 보면 방향이 이미 정해져 있다: **흰 배경 / 얇은 회색 보더 / 라운드 카드 / 초록 포인트(다로리 브랜드) / 경고는 주황.** 이 톤을 따른다.

쓰는 사람은 다로리인 운영 담당자다. **어르신용 화면이 아니다.** 매니저·요청자 앱의 큰 글씨/큰 버튼 규칙을 가져오면 안 된다. 정보 밀도를 올리고 **숫자와 상태 배지의 가독성**에 집중한다.

### 3-2. 참고할 대시보드

| 레퍼런스 | 훔칠 것 |

| **Stripe Dashboard** | 돈을 여러 상태로 쪼개 보여주는 방식. 2-6 예산 카드의 원형 |
| **Linear** | 사이드바 + 밀도 높은 목록 |

**TanStack Table을 넣은 이유**: 원문 `admin-managers` 표가 컬럼 12개 + 하단 합계 행이다. 직접 만들면 시간이 많이 든다.

## 4. 제작 순서 및 필요 사항

### 4-1. 핵심 전략 — 데이터 통로를 한 겹으로

DB가 미정이므로 **데이터를 가져오는 코드를 전부 한 폴더에 가둔다.**

```
lib/
├ types.ts          ← 데이터 모양과 상태 값 정의. 가장 먼저 확정
├ data/
│  ├ index.ts       ← 화면이 쓰는 유일한 창구
│  ├ mock.ts        ← 지금: 가짜 데이터
│  └ real.ts        ← 나중: 개발자 DB 연결
└ calc.ts           ← 금액 계산식만 모아둔 곳
```

화면 코드는 **절대** DB를 직접 부르지 않고 `lib/data` 만 호출한다. 설정 하나로 가짜/진짜를 전환한다.

**이게 이 프로젝트에서 가장 중요한 설계 결정이다.** 이것만 지키면 DB가 무엇이든 상관없어진다.

### 4-2. 단계별 순서

**원칙: 계산식 → 계산식을 쓰는 화면 → 요약 화면.** 정산 로직이 확정되지 않으면 대시보드 KPI를 정의할 수 없다.

| Phase | 할 일 | 예상 |
|---|---|---|
| **0. 준비** | `CLAUDE.md` 작성, `types.ts`(상태 값 확정), 가짜 데이터 설계 | 반나절 |
| **1. 껍데기** | Next.js 셋업, 사이드바 7메뉴, 9개 화면 빈 페이지, 로그인 차단 | 반나절 |
| **2. 가짜 데이터** | 매니저 6명, 대상자 20여명, 일지 50여건, 9개 읍면 **불균형** 분포 | 반나절 |
| **3. 계산식** ★ | `calc.ts` — 산정액·잔액·사용률·4단계 금액 + **테스트** | 1일 |
| **4. 일지 검토** ★ | `admin-review` 카드 목록·필터·승인·반려 | 1~2일 |
| **5. 활동비·설정** ★ | `admin-payments`(정산 2단 승인 구조), `admin-settings` | 1~2일 |
| **6. 매니저·대상자** | `admin-managers`(12컬럼+합계행), `admin-recipients` | 2일 |
| **7. 대시보드** | 탭 1·2·3 KPI·표·차트, 검토 배너 | 1~2일 |
| **8. 지도** | GeoJSON 확보 → 단계구분도 → 라벨 → 부족 판정 → 범례·툴팁 | 1~2일 |
| **9. 요청 현황** | `admin-requests` | 반나절 |
| **10. DB 연결** | `real.ts` 구현, 가짜 데이터 결과와 대조 | 개발자 DB 후 |

**Phase 3을 먼저 하는 이유:** 이 프로젝트에서 유일하게 "틀리면 안 되는" 부분이다. UI는 나중에 고치면 되지만 **잘못 계산된 활동비는 이미 지급된 뒤에 발견된다.** 특히 2-6의 4단계 금액 구분은 계산식이 4개다.

## 5. 바이브 코딩 참고사항

### 5-1. `CLAUDE.md` 부터

프로젝트 폴더에 이 파일을 두면 Claude Code가 매 세션 자동으로 읽는다. **없으면 매번 같은 설명을 반복하게 된다.**

```markdown
# 다로리 관리자 대시보드

## 무엇
청도군 돌봄매니저 양성사업 운영 관리 웹 (관리자 전용, 별도 사이트).
기존 HWP 활동일지 + 엑셀 정산을 대체하는 것이 목적.
근거 문서: 앱 기획서 Ver 1.0

## 스택
Next.js App Router / TypeScript / Tailwind / shadcn/ui
Recharts / react-simple-maps / TanStack Table

## 절대 규칙
- 화면 컴포넌트는 DB를 직접 호출하지 않는다. 반드시 lib/data 경유
- 금액은 정수(원). 소수점 금지
- 금액 계산은 lib/calc.ts 안에서만. 컴포넌트 안에서 계산 금지
- 상태 문자열은 lib/types.ts 에 정의된 값만 사용
- 가짜 데이터에 실제 개인정보를 넣지 않는다

## 기획서 규칙 (임의로 바꾸지 말 것)
- 승인된 일지만 정산에 포함
- 정산은 2단계: 정산 생성 → 정산 승인 → 그때 잔액 적립
- 재산정은 미승인 건만 갱신
- 승인 취소는 잔액이 음수가 안 될 때만
- 비활성·삭제 매니저도 지급 이력 있으면 표에 유지
- 예산 카드는 지급완료 / 승인미지급 / 승인대기 를 반드시 분리 표시
- active 매니저만 요청 배정·일지 작성 가능

## 하지 말 것
- 자동 승인 / AI 자동 분류 제안
- 요청 유형과 활동 유형을 한 차트에 합치기 (변환 규칙 미확정)
- 요청하지 않은 라이브러리 추가
- 요청하지 않은 파일 대량 생성

## 용어
관리자=admin(다로리인) / 매니저=helper / 요청자=recipient
```

### 5-2. Claude Code vs Cursor

| | Claude Code | Cursor |
|---|---|---|
| 잘하는 것 | 여러 파일 걸친 기능 구현, 구조 설계, 테스트 실행 | 보고 있는 파일의 부분 수정 |
| 쓸 때 | "`admin-review` 화면 만들어줘" | "이 여백만 줄여" |
| 이 프로젝트 | **메인. Phase 0~10 전부** | Phase 8 이후 디테일 조정만 |

**Phase 0~7은 Claude Code만 쓴다.** 두 도구를 섞으면 같은 파일을 서로 다르게 고쳐서 꼬인다.

### 5-3. 프롬프트 패턴

**❌** "관리자 대시보드 만들어줘"
→ 20개 파일이 쏟아지고, 내가 이해 못 하는 코드가 되고, 고칠 때마다 다른 데가 깨진다.

**✅**
> "`lib/types.ts` 의 `ActivityLog` 타입 기준으로 `admin-review` 페이지를 만들어줘.
> 기획서 명세는 이래: 필터는 월·상태·매니저 3개. 목록은 **카드 형식**이고 카드 안에
> 대상자/매니저, 활동일시·유형, 활동장소, 참여인원, 활동내용, 특이사항, 사진, GPS 위치·거리가 들어가.
> 데이터는 `lib/data` 의 `listLogs` 만 호출해.
> 승인/반려 버튼은 UI만 만들고 동작은 다음에 붙일게.
> shadcn/ui를 쓰고 새 라이브러리는 추가하지 마."

**좋은 프롬프트 5요소:** ① 범위를 한 화면으로 ② 기준 파일 지정 ③ **기획서 명세를 그대로 붙여넣기** ④ 데이터 출처 명시 ⑤ 이번에 하지 말 것 명시

**③이 이 프로젝트의 핵심이다.** 2장 명세를 복사해서 프롬프트에 붙이면 원문과 어긋날 일이 없다.

### 5-4. 실전 팁

**계획 먼저, 코드 나중.** 큰 작업은 "코드 쓰지 말고 계획부터 보여줘"로 시작한다. (Claude Code에서 Shift+Tab)

**Git 커밋을 Phase 단위로.** 가장 무서운 건 "잘 되던 게 언제부터 깨졌는지 모르는 상태"다.

**계산식은 눈으로 말고 테스트로.**
> "`calc.ts` 함수들에 vitest 테스트를 써줘. 잔액이 정확히 0인 경우, 잔액 초과 출금 신청, 승인 취소로 음수가 되는 경우, 단가 변경 후 재산정, 그리고 지급완료+승인미지급+승인대기 합이 맞는지를 반드시 포함해."

**"왜 이렇게 했어?"를 물어라.** 특히 `calc.ts` 는 **내가 완전히 설명할 수 있어야 한다.** 금액이 틀렸을 때 원인 찾는 건 내 몫이다.

**가짜 데이터를 일부러 불균형하게.** 데이터가 고르면 "매니저 부족 지역" 판정이 아예 안 걸려서 로직 검증이 안 된다. 매니저 0명인 면을 반드시 몇 개 만들 것.

### 5-5. 조심할 것

| 함정 | 대응 |
|---|---|
| 예산 카드를 "총액" 하나로 뭉갬 | 🟦 4단계 분리가 원문 규칙. 내가 이미 한 번 틀린 부분 |
| 정산 승인을 일지 승인과 합침 | 🟦 승인은 두 번이다 |
| 매니저 삭제 시 지급 이력도 삭제 | 🟦 이력 있으면 표에 유지 |
| 임의로 라이브러리 추가 | package.json 변경 확인 |
| 계산식을 화면 안에 인라인 | `calc.ts` 밖 계산은 무조건 되돌리기 |
| 가짜 데이터에 실명·실주소 | 유출 사고 |
| 금액을 소수점으로 | 정수 원 단위 |

### 5-6. 세션 시작 루틴

1. `git status` 로 깨끗한 상태 확인
2. 이번 세션에 만들 **화면 하나**를 정한다
3. 2장에서 해당 화면 명세를 복사해 프롬프트에 붙인다
4. 계획 먼저 받고 → 읽고 → 고치고 → 실행
5. 브라우저에서 확인 → 커밋

```
다로리 관리자 대시보드를 만든다. 오늘은 Phase 0~1만.

프로젝트: 청도군 돌봄매니저 양성사업 운영 관리 웹 (관리자 전용 별도 사이트).

스택: Next.js App Router + TypeScript + Tailwind + shadcn/ui

오늘 할 것:
1. CLAUDE.md 작성 (내용 줄게)
2. lib/types.ts — 데이터 타입과 상태 값
   Manager, Recipient, CareRequest, ActivityLog, Settlement, Payout, Settings
   확정된 상태값:
     매니저: applied | educated | active | inactive
     요청:   requested | proposed | confirmed | completed | cancelled
   미확정(임시로 이렇게 두고 나중에 바꿀 수 있게):
     일지:   pending | approved | rejected
     출금:   requested | paid | rejected
     정산:   calculated | approved
3. lib/data/index.ts — 데이터 접근 인터페이스만 정의 (구현은 아직)
4. 앱 껍데기: 좌측 사이드바 7메뉴
   (대시보드 / 요청 현황 / 일지 검토 / 대상자 관리 / 매니저 관리 / 활동비 관리 / 설정)
5. 각 경로에 빈 페이지 (제목만)

오늘은 데이터도 스타일 디테일도 넣지 마. 클릭해서 이동되는 뼈대까지만.
먼저 계획을 보여주고, 내가 확인한 다음 실행해.
```
