## 0. 배경 — 왜 고치는가

대시보드 액션 큐(`app/page.tsx`)의 `detail` 문구 8개가 형식이 제각각이다.
그중 5개는 **`label`을 다시 설명하는 완결형 문장**이라, 관리자가 8줄을 스캔할 때
매번 문장을 읽어야 한다.

```
❌ 정산 필요        · 승인됐지만 아직 매니저에게 안 나갔습니다
❌ 매니저 심사 대기 · 다음 단계 진행이 필요합니다            ← 정보량 0
❌ 배정 예산 미설정 · 이번 달 배정 예산이 설정되지 않았습니다  ← 라벨 반복
```

원인은 말투가 아니라 **정보 구조**다. `detail` 칸에 넣을 새로운 사실이 없으니까
문장으로 채웠고, 문장이 되니까 종결어미가 붙었다.

→ **해결: `detail`에 실제 판단 근거를 넣고, 형식을 하나로 고정한다.**
일부 항목은 `ActionQueue` 타입 확장이 필요하다. 전부 기존 데이터에서 계산 가능하다.

## 1. 절대 지킬 것

`CLAUDE.md`의 절대 규칙을 그대로 따른다. 특히 이 작업에서 걸리는 것:

1. **계산은 `lib/calc.ts` 안에서만.** `app/page.tsx`의 `buildActionItems()`는
   문자열 조립만 한다. 필터·집계·날짜 계산을 컴포넌트로 끌어오지 말 것
2. **상태 문자열 직접 사용 금지.** `lib/status.ts` 상수만
3. **`lib/status.ts`의 한글 라벨은 이번 작업에서 건드리지 않는다.**
   기획서 원문 표기라 변경하려면 기획 담당자 확인이 먼저다 (5장 참고)
4. 새 라이브러리 추가 없음. 새 파일 생성 없음 (기존 파일 수정만)

## 2. 작업 A — `ActionQueue` 타입 확장

`CLAUDE.md`의 데이터 흐름 순서대로 간다: **types → calc → test → mock → 화면**

### A-1. `lib/types.ts` — `ActionQueue`에 필드 추가

기존 필드는 그대로 두고 아래를 추가한다. 주석 표기는 🟨(임시·제안).

```ts
export interface ActionQueue {
  // ── 기존 유지 ──
  approvedUnpaid: Won
  requestedPayoutCount: number
  pendingLogCount: number
  oldestPendingDays: number
  staleRequestCount: number
  pendingManagerCount: number
  unassignedRecipientCount: number
  shortageRegions: Region[]
  needsBudgetSetup: boolean

  // ── 신규 (detail 표시 전용) ──
  /** 🟨 1. 잔액(=승인 미지급)이 남아 있는 매니저 수 */
  unpaidManagerCount: number
  /** 🟨 2. requested 상태 출금 중 가장 오래된 건의 경과 일수. 없으면 0 */
  oldestRequestedPayoutDays: number
  /** 🟨 5. 심사 대기 인원의 단계별 분해 (applied / educated) */
  appliedManagerCount: number
  educatedManagerCount: number
  /** 🟨 6. 미배정 대상자의 읍·면 분해. count 내림차순 */
  unassignedByRegion: { region: Region; count: number }[]
  /** 🟨 8. 배정 예산이 미설정된 대상 월 */
  budgetSetupMonth: YearMonth
}
```

### A-2. `lib/calc.ts` — 계산 함수 4개 추가

기존 `oldestPendingDays` / `pendingManagerCount` 바로 아래, 액션 큐 섹션 안에 넣는다.

```ts
/** 잔액이 남아 있는 매니저 수 = 승인 미지급이 걸린 인원 */
export function unpaidManagerCount(
  managers: Manager[],
  settlements: Settlement[],
  payouts: Payout[],
): number

/** requested 출금 중 가장 오래된 건의 경과 일수. 없으면 0 */
export function oldestRequestedPayoutDays(payouts: Payout[], now: Date): number

/** 심사 대기 인원 단계별 분해 */
export function managerReviewBreakdown(
  managers: Manager[],
): { applied: number; educated: number }

/** 미배정 대상자의 읍·면별 분해. count 내림차순, count 0인 지역은 제외 */
export function unassignedRecipientsByRegion(
  recipients: Recipient[],
): { region: Region; count: number }[]
```

**구현 시 주의**

- `unpaidManagerCount` — 매니저별 잔액은 기존 `calcBalance()`를 재사용한다.
  새로 계산식을 쓰지 말 것. `balance > 0` 인 매니저만 센다.
  `deletedAt`이 있어도 잔액이 남아 있으면 포함한다
  (기획서: 삭제된 매니저도 지급 이력이 있으면 표에 유지)
- `oldestRequestedPayoutDays` — `oldestPendingDays()`와 동일한 패턴·동일한 내림 처리
  (`Math.floor`, 밀리초 → 일)
- `unassignedRecipientsByRegion` — `unassignedRecipientCount()`와 **판정 조건이 반드시 같아야
  한다** (`!r.deletedAt && !r.managerId`). 두 곳에서 갈리면 총합이 안 맞는다.
  동률일 때 순서가 흔들리지 않게 count 내림차순 → 지역명 오름차순으로 2차 정렬

### A-3. `lib/calc.test.ts` — 신규 함수 4개 테스트 추가

기존 `describe` 블록 스타일을 그대로 따른다. 각 함수마다 최소:

- 정상 케이스 1개
- **빈 배열 → 0 / `[]`**
- 경계 케이스:
  - `unpaidManagerCount` — 잔액이 정확히 0인 매니저는 세지 않는다
  - `oldestRequestedPayoutDays` — `paid`·`rejected` 출금은 무시한다
  - `unassignedRecipientsByRegion` — `deletedAt` 있는 대상자는 제외,
    동률 지역의 정렬 순서가 고정인지

> `unassignedRecipientsByRegion`의 합계 == `unassignedRecipientCount` 인지
> 검증하는 테스트를 1개 넣을 것. 이게 깨지면 화면 숫자가 어긋난다.

### A-4. `lib/data/mock.ts` — `getDashboard`의 `actions` 블록 채우기

`actions: { ... }` 객체에 신규 필드를 추가한다. **계산은 전부 `lib/calc.ts` 함수 호출로.**
목 데이터에서 직접 `.filter()` 돌리지 말 것.

`budgetSetupMonth`는 `getDashboard(yearMonth)`의 인자 `yearMonth`를 그대로 쓴다.

> `new Date()`가 이미 두 번 호출되고 있다. 신규 함수까지 더해지면 4번이 된다.
> 함수 상단에서 `const now = new Date()` 한 번만 만들어 넘길 것 (일관성).

## 3. 작업 B — `app/page.tsx` detail 포맷 통일

### B-1. 포맷 규칙

```
{숫자+단위} · {판단에 필요한 분해값 또는 경과 기간}
```

- 완결형 문장 금지. 종결어미(`~습니다`, `~합니다`, `~중`) 금지
- 구분자는 가운뎃점 ` · ` (앞뒤 공백 포함) 하나로 통일
- 넣을 사실이 없으면 detail을 짧게 두거나 비운다. **문장으로 채우지 않는다**

### B-2. 8개 항목 목표값

| key | label | detail (변경 후) |
|---|---|---|
| `approved-unpaid` | 정산 필요 | `₩1,240,000 · 매니저 6명분` |
| `requested-payout` | 출금 신청 대기 | `3건 · 최장 5일 경과` |
| `pending-log` | 일지 검토 대기 | `12건 · 최장 8일 경과` |
| `stale-request` | 배정 지연 요청 | `2건 · 24시간 초과` |
| `pending-manager` | 매니저 심사 대기 | `2명 · 신청 1 · 교육이수 1` |
| `unassigned-recipient` | 미배정 대상자 | `4명 · 화양읍 3 · 금천면 1` |
| `shortage-region` | 매니저 부족 지역 | `2곳 · 운문면, 각북면` |
| `budget-setup` | 배정 예산 미설정 | `2026-08` |

`label`은 **8개 모두 현행 유지.** 이미 명사구로 잘 되어 있다.

### B-3. 예외 처리 (중요)

문구가 깨지는 건 대부분 0·1개 케이스다. 반드시 처리한다.

| 상황 | 출력 |
|---|---|
| 경과 일수가 0일 (오늘 들어온 건만) | `3건` — ` · 최장 0일 경과` 붙이지 않는다 |
| 심사 대기 단계 중 한쪽이 0 | `2명 · 신청 2` — 0인 단계는 생략 |
| 미배정 지역이 3곳 이상 | 상위 2곳만 + `외 2곳` → `9명 · 화양읍 4 · 금천면 3 · 외 2곳` |
| 미배정 지역 정보가 비었을 때 | `4명` — 뒤를 붙이지 않는다 |
| 부족 지역이 5곳 이상 | 상위 3곳 + `외 N곳` (한 줄이 넘치지 않게) |

### B-4. 하드코딩 제거

`stale-request`의 `"24시간"`은 현재 문자열에 박혀 있다.
`lib/calc.ts`의 `STALE_HOURS`를 import해서 `${STALE_HOURS}시간 초과`로 바꾼다.
(`app/requests/page.tsx`는 이미 그렇게 하고 있다. 두 화면의 기준이 갈리면 숫자가 안 맞는다)

### B-5. `formatWon` 유지

`approved-unpaid`의 금액은 `formatWon()` 그대로 쓴다.
표·카드에서 금액 축약은 금지되어 있다 (`CLAUDE.md` 디자인 규칙).

## 4. 작업 C — 나머지 문구 5건

작업 A·B와 독립적이고 위험도가 낮다. 한 커밋으로 묶어도 된다.

### C-1. `app/page.tsx:330` — 차트 캡션 교체

```
❌ 제출과 승인의 간격이 벌어질수록 검토가 밀리고 있다는 신호입니다.
```

차트 밑에서 해석을 대신 해주는 문장. 차트는 스스로 말해야 한다.
**가장 최근 달의 실제 수치**로 바꾼다.

```
⭕ 미승인 12건 · 제출 34 / 승인 22
```

`data.trend.at(-1)`에서 계산한다. `submitted - approved`가 0이면 캡션 전체를 렌더하지 않는다.

### C-2. `app/requests/page.tsx:143~146` — 배지 설명 배너 제거

```
❌ "배정 지연" 배지가 붙은 건은 접수된 지 24시간이 지나도록 시간 제안이 없습니다.
```

배지 정의를 상시 배너로 띄우면 매번 읽고 넘겨야 한다.
배너 블록을 삭제하고, 같은 내용을 **`배정 지연` 배지 자체의 `title` 속성**으로 옮긴다.

```tsx
title={`접수 후 ${STALE_HOURS}시간 경과, 시간 제안 없음`}
```

### C-3. `app/recipients/page.tsx:394` — 마스킹 버튼 라벨

```
❌ ●●●● 보기        ⭕ 주소 보기
```

마스킹 문자를 버튼 라벨로 쓰면 무엇을 여는 건지 알 수 없다.
셀 안의 마스킹 표시(`●●●●`) 자체는 유지한다. 바꾸는 건 **버튼 라벨뿐**이다.

### C-4. `components/layout/topbar.tsx:7` — 기간 표시 제거

```
❌ 기간: 이번 달 ▾
```

`▾`를 텍스트로 넣었고, 대시보드에 월 `Select`가 따로 있어 기능이 중복된다.
**동작하지 않는 요소라면 제거한다.** 실제로 붙일 계획이 있으면 그대로 두고 보고할 것.

### C-5. `app/review/page.tsx:105, 119` — 에러 어미 통일

프로젝트 전체가 `~하지 못했습니다`인데 이 두 곳만 다르다.

```
❌ 승인 처리 중 오류가 발생했습니다   →  ⭕ 승인하지 못했습니다
❌ 반려 처리 중 오류가 발생했습니다   →  ⭕ 반려하지 못했습니다
```

## 5. 하지 말 것

- **`lib/status.ts`의 한글 라벨 변경 금지.**
  `승인` / `지급 완료` / `산정`의 종결 형태가 제각각인 문제는 인지하고 있으나,
  이 라벨들은 **기획서 원문 표기**다. 기획 담당자 확인 전까지 손대지 않는다
- **`label` 8개 변경 금지.** 이번 작업 범위는 `detail`이다
- **액션 큐 항목 추가·삭제·순서 변경 금지.** 문구만 고친다
- 계산 로직을 `app/page.tsx`로 끌어오지 말 것
- 요청하지 않은 리팩터링·파일 생성 금지
